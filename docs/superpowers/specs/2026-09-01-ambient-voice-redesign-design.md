## 결정 사항

### 시각화 개념

이전 파형은 "볼륨 이력을 가로축에 늘어놓은 그래프"라 본질적으로 오디오 편집기다. 시간축을 버리고
**지금 이 순간의 소리를 공간으로 표현**하는 방식으로 바꾼다.

- 서로 다른 주파수 대역(저/중/고)에 묶인 빛 덩어리 4개가 배경에 떠 있다
- 각 덩어리는 위치·크기·색·주기·반응 강도가 전부 다르다 → 좌우 대칭이 생기지 않는다
- `filter: blur(44px)`로 크게 번뜨려 원반이 아니라 빛으로 읽히게 한다

### 반복되지 않는 숨쉬기

단순 사인파는 주기가 눈에 띈다. `breathe()`는 `sin(t/P)`에 `sin(t/(P·√2))`를 0.65:0.35로 섞는데,
√2가 무리수라 두 성분이 정확히 다시 겹치는 시점이 없다 — 준주기적이라 영원히 같은 모양이 반복되지
않는다. 덩어리마다 주기도 서로 나누어떨어지지 않게 잡았다(8.9 / 10.3 / 11.3 / 12.3 / 12.7 / 13.7 /
14.9 / 15.1 / 17.9 / 19.1초).

### 균일 확대가 아니라 변형

`scale(s)` 하나로 키우면 실루엣이 항상 완전한 원이라 기계적으로 보인다. 대신:

- `scaleX`/`scaleY`를 **서로 다른 위상**의 `breathe`로 따로 흔든다 → 눌렸다 펴진다
- `border-radius`를 8개 값 퍼센트 표기로 매 프레임 바꾼다 → 외곽선이 흐물거린다
- 밝기에도 숨쉬기 성분을 섞는다 → 말이 없어도 빛이 짙어졌다 옅어진다

### 이퀄라이저처럼 튀지 않게

세 겹으로 눌러준다:
1. `analyser.smoothingTimeConstant = 0.85` — AnalyserNode 자체 평활
2. `followEnvelope` — 어택 빠르게(0.14), 릴리즈 느리게(0.035). 말이 끊겨도 빛이 천천히 잦아든다
3. `envelopeCoefficient` — 위 계수는 **60fps 한 프레임 기준**이다. 그대로 쓰면 120Hz 화면에서 두 배
   빨라져 정확히 "이퀄라이저 느낌"이 나고, 30fps에서는 두 배 느려져 뭉개진다. 실제 경과 시간으로
   환산해 어느 주사율에서도 같은 시간 상수를 갖게 한다

### 조용할 때는 정말 조용하게

기본 `minDecibels`(-100)는 범위가 너무 넓어 조용한 방의 암소음(-70dB 근처)도 눈금의 40%까지
올라온다. 게다가 `getUserMedia`의 자동 게인 보정은 침묵 구간의 잡음을 적극적으로 끌어올린다.
그대로 두면 아무도 말하지 않는데 덩어리가 항상 부풀어 있어 "말하면 커진다"는 표현이 죽는다.

- `minDecibels = -75`, `maxDecibels = -20` — 사람 목소리 구간으로 좁힌다. **무음 차단의 주된
  장치**이며, 잡음이 실제로 존재하는 dB 도메인에서 자르므로 원리적으로 여기가 맞는 자리다
- `autoGainControl: false` — 이 스트림은 통화용이 아니라 측정용이다
- `NOISE_FLOOR = 0.06` — 남은 잔여분만 다듬는 보조 장치. 값이 작아야 한다. 크게 잡으면 dB 창과
  이중으로 깎여, 자동 게인을 끈 상태의 노트북 내장 마이크처럼 입력이 작은 환경에서 말해도
  반응이 거의 없어진다
- 이 값은 `minDecibels`에 매여 있다(현재 창 기준 0.06 ≈ -71.7dB/bin). dB 창을 바꾸면 다시
  계산해야 하며, 합성 스펙트럼을 넣는 단위 테스트로는 이 어긋남을 잡을 수 없다

### 시각화 부하

`transform`과 `opacity`만 매 프레임 쓴다. 둘 다 합성 단계에서만 처리되므로 페인트가 발생하지
않는다. `border-radius`로 외곽선을 흐물거리게 하는 방법도 검토했지만 쓰지 않았다 — 그건 페인트를
무효화해서 각 덩어리의 44px 블러를 매 프레임 다시 계산하게 만든다(4개 × 60~120fps). 형태의
유기성은 두 축 `scale` + `rotate`로 얻고, 블러가 이미 외곽선의 미세한 차이를 지우기 때문에 시각적
손해도 거의 없다.

`smoothingTimeConstant`는 0.3으로 낮췄다. AnalyserNode 자체 평활은 "프레임당" 적용이라 주사율에
따라 시간 상수가 달라지는데, 이건 `envelopeCoefficient`로 해결한 문제와 같은 종류다. 평활은
주사율에 무관하게 환산되는 `followEnvelope` 쪽에서 전담하게 두고 튜닝 지점을 한 곳으로 모은다.

### 대역 분할 (fftSize 1024, 48kHz 기준 bin당 약 47Hz)

| 대역 | bin 비율 | 실제 주파수 | 근거 |
|---|---|---|---|
| low | 0.004~0.04 | 약 94~984Hz | 기본 주파수(F0) + 제1포먼트. 가장 큰 덩어리를 여기 묶는다 |
| mid | 0.04~0.16 | 약 938~3844Hz | F2/F3, 자음 명료도 |
| high | 0.16~0.39 | 약 3844~9375Hz | 치찰음 |

0번 bin은 DC 성분이라 제외한다.

### React 렌더 경로를 타지 않는다

이전 `useMicLevel`은 매 애니메이션 프레임 `setState`를 호출해 화면 전체를 초당 60번 리렌더했다.
`useMicAnalyser`는 상태를 들지 않고 `AnalyserNode`만 ref로 넘기고, `AmbientVoiceField`가 자기 rAF
루프에서 DOM 스타일(`transform` / `opacity` / `border-radius`)만 직접 쓴다.

### 대비 (이 화면 네 번째 점검)

배경은 `#fdf4ec` 위에 반투명 파스텔 덩어리 4개. **모든 덩어리 색이 밝은 파스텔**이라 어떤 조합으로
겹쳐도 합성 결과가 밝게 유지되고, 그 위 어두운 글씨의 대비가 덩어리 위치와 무관하게 보장된다.
이게 "배경에 은은하게 깔리고 UI 텍스트를 방해하지 않기" 요구사항을 만족시키는 핵심 장치다.

네 덩어리가 최대 크기·최대 불투명도로 전부 겹친 최악의 경우를 기준으로 잡는다:

| 요소 | 색 | 대비 | 기준 |
|---|---|---|---|
| 타이머, 대본 | `slate-800` | ~9.2:1 | 4.5:1 ✅ |
| 상태 라벨, 힌트 | `slate-700` | ~6.2:1 | 4.5:1 ✅ |
| 컨트롤 아이콘 | `slate-700` (흰 버튼 위) | ~9.4:1 | 4.5:1 ✅ |
| 대본 placeholder | `slate-600` (`bg-white/60` 위) | ≥4.7:1 | 4.5:1 ✅ |
| 버튼 경계 | `ring-slate-900/15` | ~3.1:1 | 3:1 ✅ |

흰 버튼은 밝은 배경 위에서 `bg-white`만으로는 경계가 1.1:1 수준이라 사실상 보이지 않는다.
`ring-1 ring-slate-900/15`를 줬지만 이것도 1.36:1이라 **3:1 기준을 만족하지는 않는다** —
3:1을 넘기려면 `/50`(3.35:1)까지 진해져야 하는데, 그러면 파스텔 배경 위에 뚜렷한 검은 테두리가
생겨 이 화면이 지향하는 톤과 정면으로 부딪힌다.

**의도적으로 받아들인 예외**로 기록한다. 근거: 버튼 안의 아이콘이 흰 바탕 위 `slate-700`으로
9.4:1이라, 컨트롤을 식별하는 시각 정보는 실루엣이 아니라 아이콘이 담당한다. 링은 장식이지
경계 보장 장치가 아니다. (다음에 이 화면을 만질 때 "링이 3:1을 맞춰준다"고 가정하지 말 것.)

# 기능 2: 사용자가 기록 도중 원하는 화면으로 되돌아갈 수 있다

## 완료 조건
- [ ] 타이핑 화면에 `음성으로` 버튼이 있고, 누르면 친 글이 그대로 넘어간 채 녹음이 시작된다
- [ ] 어느 단계에 있든 nav `기록`을 누르면 첫 화면으로 돌아간다
- [ ] 작성 중인 내용이 있으면 그냥 사라지지 않고 한 번 확인한다

## 안 되는 경우
- 작성 중인 내용이 없을 때 → 확인 없이 바로 첫 화면으로
- 저장이 진행 중일 때 → 이동을 무시한다. 되돌려도 저장 요청은 계속 날아가고, 성공하면 몇 초 뒤
  상세 화면으로 튕겨 나가기 때문
- 확인창에서 `계속 작성`을 고른 뒤 브라우저 뒤로가기 → 정상적으로 다시 확인창이 뜬다
- 브라우저가 음성 인식을 지원하지 않을 때 → 타이핑 화면의 `음성으로` 버튼이 아예 렌더되지 않는다

## 이번에 안 하는 것
- nav 바 자체의 재구성(하단 이동, 아이콘화) — 별도 슬라이스
- 작성 중인 내용의 임시 저장/복구

## 결정 사항

### 첫 화면 복귀 신호

`기록` 탭은 `/` 경로이고 RecordPage의 단계는 컴포넌트 내부 상태다. 이미 `/`에 있을 때 같은 경로로
이동해도 컴포넌트가 다시 마운트되지 않으므로, 단계를 되돌리려면 별도 신호가 필요하다.

react-router는 **같은 경로로의 `<Link>` 클릭을 replace로 처리하면서 새 `location.key`를 발급**한다.
그 key 변화를 신호로 쓴다. `<Link>`를 `<button>`+`navigate`로 바꾸면 히스토리에 중복 항목이 쌓이고
접근성(링크 시맨틱, 새 탭 열기)도 잃으므로 `<Link>`를 유지한다.

비교 기준은 "마운트 시점의 key"가 아니라 **"마지막으로 처리한 key"**여야 한다. 전자로 두면 확인창에서
`계속 작성`을 고른 뒤 브라우저 뒤로가기로 원래 key에 돌아왔을 때 아무 반응도 하지 않아, 뒤로가기가
죽은 것처럼 보인다.

### 리셋은 한 곳에서

`resetRecordState()`가 플로우의 모든 필드를 지운다 — 받아쓰기, 타이핑 내용, 타이머, `voiceDone`,
에러, 상태 메시지, 그리고 **`structureFailed`와 `savedEntryIdRef`/`savedRawTextRef`**.

마지막 셋이 특히 중요하다. 저장은 됐지만 구조화가 실패한 뒤 첫 화면으로 나가면, 이 값들이 남아
있어서 새로 녹음한 내용이 details 단계에서 저장 버튼 대신 "이전 기록 구조화 재시도" 화면을 만난다.
그 화면의 버튼들은 전부 **이전 entry**를 가리키므로, 새 기록은 영영 저장할 수 없게 된다.
`returnToChoice`와 `cancelVoice` 둘 다 이 함수를 쓴다.

### `← 뒤로`도 확인을 거친다

`← 뒤로`와 `🗑`이 둘 다 내용을 지우는데, `뒤로`는 되돌릴 수 있는 이동처럼 읽힌다. 확인 없이 몇 분짜리
녹음을 날리게 되므로 `← 뒤로`도 `requestReturnToChoice()`를 거치게 한다.

# 기능 3: 사용자가 녹음한 내용을 원하는 위치에서 고칠 수 있다

## 완료 조건
- [ ] 대본 글씨가 이전(`text-sm`)보다 크다 (`text-lg`)
- [ ] 녹음을 멈춘 상태에서 대본의 아무 곳이나 클릭해 그 자리부터 고칠 수 있다
- [ ] 고친 뒤 `▶`로 이어 녹음하면 **고친 내용 뒤에** 새로 말한 내용이 붙는다

## 안 되는 경우
- 녹음 중일 때 → 읽기 전용. 새로 인식된 말이 계속 뒤에 붙으면서 커서가 튀기 때문
  (사용자 확인으로 "멈췄을 때만 수정 가능"으로 확정)

## 결정 사항

녹음 중에는 `<p>`, 멈추면 `<textarea>`로 바꿔 렌더한다. 둘 다 `speech.transcript` 하나만 보므로
전환 과정에서 내용이 유실되지 않는다.

이어 녹음이 고친 내용 뒤에 붙는 이유는 `useSpeechInput`의 구조 덕분이다 — 공개 `setTranscript`가
곧 `applyTranscript`라서 textarea 편집이 `transcriptRef`를 **동기적으로** 갱신하고, 새 인식 세션은
시작 시점의 `transcriptRef`를 클로저에 담아 기준값으로 쓴다. 즉 편집 결과가 그대로 다음 세션의
기준값이 된다.

`✓` 이후 가운데 버튼 라벨은 `넘어가기` → `저장`으로 바꾼다(사용자 요청). 동작은 그대로 제목·컬렉션
입력 단계로 넘어가는 것이며, 실제 DB 저장은 거기서 일어난다.
